# 事件格式

所有来源（GitHub、后台、HubSpot、Slack）的记录，先整理成同一种事件，再生成页面。事件由 `replay/events.py` 产生，文字全部来自固定模板，时间、人、原话都取自原始记录。

## 公共字段

| 字段 | 含义 |
|---|---|
| `key` | 事件的唯一标识，来自原始记录的 ID（如 `gh:feed-mob/feedmob#14633:c123`、`fm:226548`、`hs:5087:created`），同一条记录不会重复出现 |
| `ts` | 发生时间，UTC，精确到秒 |
| `src` | 来源：`github` / `femini` / `hubspot` / `slack` |
| `kind` | 动作类型：create 建单、assign 指派、label 标签流转、comment 评论、pr 提交代码/请求评审、review 评审、merge 合并、close 关单、change 后台调整、chat 聊天、notify 机器人播报 |
| `actor` | 谁做的（人物 ID） |
| `to` | 对谁（被指派人、被请求评审人、被 @ 的人） |
| `ticket` | 属于哪张单子（没有则为空） |
| `link` | 原始记录的链接 |
| `stage` | 单子走到哪一步：建单 / 安排 / 开发 / 评审 / 合并 / 自检 / 验证 / 关单 |
| `margin` | 后台调整后的利润率（只有后台调整事件有） |
| `baton` | 这一步是否把单子交到了别人手上 |
| `flag` | 需要注意的动作（如被打回），带说明文字 |

中英文各一套文字：`title`（标题）、`text`（说明）、`quote`（原话）、`ref`（出处）、`meta`（附加信息）。

## 各来源怎么变成事件

- **GitHub**：建单、指派（动手的是 assigner，不是被指派人）、标签变化（同一人 2 秒内的连续变化合并为一条）、评论、关闭/重开；关联的代码合并请求的创建、请求评审、评审结果、合并。
- **后台**：已批准的调整（利润率、单价、上限、状态等），时间取批准时间；起草时间用来写「起草后多久批准」。
- **HubSpot**：工单的建单事件（取秒级时间）和备注；没有状态变更历史，不伪造。
- **Slack**：只收录明确写了该 click URL 编号或相关 GitHub 单号的消息；机器人同一天的重复播报只留一条。

## 谁手上有单子

按时间顺序推算每张单子当前在谁手上：建单人 → 被指派人 → 被请求评审的人 → 评审完成后移出 → 合并后评审人移出 → 关单后清空。只在发生变化的事件上记录。

## 来源怎么发现（按活动）

以活动（campaign）为单位。先在后台找出活动下的链接（最多 12 条，编号大的优先；其余在页面「核对」里列出），再对每条链接分别取数，最后把记录合在一起，同一条记录被多条链接命中时只留一份。

1. 活动与链接：`get_campaign` 取活动信息，`list_click_urls(campaign_id)` 取它下面在用的链接。没有在用的链接（活动在后台停用了，或链接都停用了）就沿用上次取到的链接照常回放，首页那一行和两版页面顶栏标「已停用」（看 `campaign.active`）；从没取到过链接才明确失败。下拉列表来自 `list_campaigns`（在跑的活动）。
2. 后台：对每条链接 `get_click_url`，拿到渠道和全部调整记录。
3. GitHub：按链接编号搜；只展开标题或正文真的写了该编号的单子（每条链接最多 8 张，最近更新的优先，其余在页面「核对」里列出）；只在评论里提到的单子只记数量，不展开。
4. 大脑：用链接编号、活动名、单号去搜，只把搜索结果当线索，每个线索页都核对正文真的写了编号或单号才算；确定相关频道（最多 8 个）后，把这些频道从最早的记录前 2 天起按天全部读一遍（有缓存）。
5. 利润率走势图：只有一条链接调过利润率时才画；多条链接都调过，混在一张图里没有意义，不画（每次调整仍在时间线里，页面「核对」里写明）。

## 不做的事

不推断没发生的事（页面底部的「接下来」明确标为推断）；不翻译中文原话；不把对不上人的账号硬凑成某个同事。
