# 异常排查（spend 录入异常）

在一个活动的回放里，选一个出问题的日子，系统找出当天前后让 spend 录错的原因，并给出三样东西：
1. **错误配置**：哪条链接、哪个设置错了，实际值是什么，应该是什么；
2. **操作人证据**：谁改的配置、谁批准的、谁手动改过 spend、谁报告了问题，每一条都附原始记录；
3. **相关工单及修复状态**：相关的 HubSpot 工单、GitHub 单子，以及问题现在修好了没有。

排查用得越多，字典越准：每条结论都会被自动验证（排查日之后发生的事：后台改动、沟通记录、GitHub），对的记下来，下次优先这样判断。字典的维护全程不需要人：学什么、留哪条、合并哪条、删哪条，都由程序和 MiniMax 决定，回归集兜底。
注意：真实使用时排查的是刚发生的异常，GitHub 里通常还没有相关单子，所以验证不能只靠 GitHub——结论先标「待验证」，系统在之后自动回访。

## 怎么用

在首页该活动那一行点「异常排查」，打开单独的排查页面（`/c/<活动编号>/diagnose`）。回放页面本身不放入口和面板（2026-11-03 定：回放页面界面不改）。排查按活动，不分渠道：同一活动的所有链接一起查。

| 输入 | 说明 |
|---|---|
| 异常日期（必选） | spend 录错的那一天。表单下方会列出最近 60 天程序发现异常信号的日期，点一下就能填入 |
| 发生了什么 / Click URL / Line item（可选） | 例如「23660 spend 未录入」「line item 63 匹配失败」。不填就扫这个活动的全部链接 |
| 前后范围 | 1 / 3 / 7 / 14 天，默认 3 天 |

一次排查一般 2–6 分钟，可以关掉面板过会儿再看。本活动的排查记录列在表单下方，点开可以重看。
每条结论下面标着自动验证的结果（一致 / 部分一致 / 矛盾 / 待验证）和依据来自哪类记录。需要公司账号登录。

排查的只是这个活动：描述里写了不属于本活动的链接编号，会提示并忽略。

## 流程

```
① 解析描述（程序）     click URL 编号对照本活动链接；line item 去合作方原始报告里反查；现象词对照字典「说法」；GitHub 单号只当文字
② 原因证据（程序）     后台配置与改动历史、spend request、每日 spend、月度调整、daily feeds、line item 反查；
                       Slack（窗口内全部频道）、HubSpot 工单、邮件、会议 —— 没有 GitHub
③ 信号（程序）         逐天按单价 / 利润率 / spend request 公式核数
④ 原因（MiniMax）      字典 + skill + 信号 + 证据 → 归类、错误配置、操作人、工单；程序逐条核对
   —— 原因结论先落盘，之后才读 GitHub ——
⑤ 验证 + 修复状态      排查日之后的后台配置改动（C）、Slack / HubSpot / 邮件（L）、GitHub（G）；
                       MiniMax 判每条结论 一致 / 部分一致 / 矛盾 / 暂无依据，并找修复动作；程序定修复状态
⑥ 学习                 有依据的结论记进字典；暂无依据的等自动回访（第 3 / 7 / 14 / 30 天）
⑦ 自动整理（定期）     MiniMax 审候选条目：保留 / 合并 / 删掉；程序把关，回归集变差就回滚
```

### GitHub 的用法

| 阶段 | 读 GitHub | 用途 |
|---|---|---|
| 建字典（`dict-build`） | 能 | 从 spend 相关单子里挖错误模式 |
| 排查原因 | **不能** | 证据包没有 GitHub；Slack 不按 GitHub 单号筛；描述里的单号不跟进；结论引用 GitHub 一律作废；字典里本案的 GitHub 例子（同链接、前后 30 天）对模型隐藏 |
| 修复状态 | 能 | 单子开 / 关、修复动作的原话 |
| 事后验证 | 能 | 验证依据之一（另外两类是之后的后台改动和沟通记录）。拿历史数据回测时 GitHub 常常已经有答案；真实使用时多半还没有 |

### 程序把关（模型只挑和判断）
- 证据编号必须存在；原话逐字核对（近似的换成原文），查无就丢；没有可核对证据也没有信号的结论整条丢掉（页面「被程序丢掉的结论」里列出）。
- 操作人的名字不由模型写：模型只指出是哪条记录，名字取自那条记录的动手人（后台改动的提交人 / 批准人、Slack 发言人、HubSpot 备注人）。只被 @ 的人不算。
- 工单状态取自 HubSpot 原始字段。英文字段里出现汉字的整段清空。

### 信号（`replay/spend_checks.py`）
| 信号 | 含义 |
|---|---|
| 暂停后仍录入 | 当天链接处于暂停状态（按生效时间算），却录入了 spend |
| 有投放无 spend | 合作方有成本 / 曝光，或按单价应有 spend，但当天没有任何 spend 记录 |
| 录入为 0 | 录了 0，但合作方有成本或明显曝光 |
| 利润率不一致 | 设了利润率，gross ≠ net / (1 − 利润率)（当天改过利润率的，前后两个值都不符才算） |
| gross / net 与单价不符 | 按事件计费：录入金额 ≠ 计费事件数 × 单价 |
| net / 成本比例异常 | net 和合作方成本的比例，与 spend request 写明的系数（如 × 95%）或此前常态不同 |
| spend 突变 | gross 相对此前 14 天中位数翻 3 倍以上或跌到 1/3 以下 |

容差：金额差 ≥ $1 且 ≥ 3%；利润率差 ≥ 1 个百分点；比例差 > 5%。

### 时间范围
- 后台配置历史：截至 D+N 的全部（出错的配置可能是很久以前设的）；
- spend 数据和沟通记录：D 前后各 N 天（spend 另取前 14 天当基线）；HubSpot 工单到 D+max(N,14)；
- 修复状态和 GitHub 验证：D−N 到 D+30。

### 修复状态
| 状态 | 条件 |
|---|---|
| 已修复 | 现在重新取数，这条链接这几天已经没有异常信号，且有修复动作（之后的后台改动、修复原话、GitHub 单子已关、HubSpot 工单已关） |
| 已处理，待数据确认 | 有修复动作，但数据仍异常或无法判断（例如任务停了，错录的 spend 还没清） |
| 处理中 | 相关 GitHub 单子或 HubSpot 工单还开着 |
| 未见处理 | 以上都没有 |

## 字典

- 种子：`config/spend_anomaly_seed.json`，19 条，全部来自 Slack 镜像里的真实案例，例子原话逐字可查。分四类：配置错误、上游 / 外部、系统缺陷、人工操作（含 5 条 line item 映射类）。
- 线上：`knowledge/spend_dictionary.json`（不入库，代码同步时排除）。第一次读时由种子生成；代码里新增的种子条目会自动并入。改动记录在 `knowledge/changelog.jsonl`。
- 建字典：`python3 -m replay dict-build` 从 GitHub 搜近 12 个月的 spend 单子，按标题模板粗分成簇，挑代表单子交 MiniMax 抽错误模式（原话逐字核对）。能对上已有条目的补例子和说法；新模式成为「候选」。报告在 `knowledge/dict_build_report.json`。
- 每个条目：信号、告警关键词、常见说法、出错的设置项、修法、例子（带来源、链接编号、日期）、战绩（确认 / 部分 / 否决 / 未验证）、状态。

### 验证与学习
全程自动，不需要人。真实使用时排查的是刚发生的异常，GitHub 里通常还没有单子，所以验证依据有三类：

| 依据 | 说明 |
|---|---|
| 之后的后台改动 | 排查日之后在后台批准的配置改动，改的正是结论里那个设置（比如暂停了自动录入、把利润率改回应有的值） |
| 之后的沟通记录 | Slack / HubSpot / 邮件里有人说明了这个原因或修了这一处 |
| GitHub | 有对应单子写明了原因 |

| 验证结果 | 字典怎么变 |
|---|---|
| 一致 | 确认 +1；加一个例子；把用户当时的描述（去掉编号）记为该条目的「说法」；案例进回归集 |
| 部分一致 | 记一次部分一致 |
| 矛盾 | 否决 +1；之后记录显示的真实原因成为新候选条目 |
| 暂无依据 | 先不记，等自动回访；最后一次回访仍没有，记「未验证」 |
| 原因阶段漏掉、之后记录显示的原因 | 成为新候选条目 |

- 每条结论只记一次，换了判断（回访补到依据、重新排查同一组参数）先撤销上一次再记。
- 自动回访：排查日之后第 3 / 7 / 14 / 30 天（只排晚于建档日的；拿历史日期回测、30 天都过去了的不用回访）。后台自动回访默认**关**（它会自己调 AI），`REPLAY_DIAG_FOLLOWUP=1` 才开，开了以后服务里每 30 分钟看一次有没有到期的；关着时手动跑 `python3 -m replay diagnose-followup`。回访会重新取之后的后台改动、沟通记录、GitHub 和当前数据，更新修复状态，只给「暂无依据」的结论补验证。
- 种子 / 候选确认满 2 次转为正式；否决满 3 次且多于确认的两倍，停用（不再给模型看）。状态完全由战绩算出，撤销后会回到原来的状态。
- 字典里由排查学来的例子和 GitHub 例子，对「同一条链接、前后 30 天」的排查隐藏，避免把答案递给模型。

### 自动整理
建字典和排查学习会不断加进候选条目，其中有重复的、有不是 spend 录错的（告警噪音、监控容差、流程规范）。MiniMax 定期审一遍（`replay/curate.py`）：

| 决定 | 程序怎么执行 |
|---|---|
| 保留 | 可以顺便把名字、说明改写清楚 |
| 合并到某条 | 同一个根因、同一个修法才合并；例子、说法、告警词、战绩都并过去，原条目标「已合并」（不删，留理由） |
| 删掉 | 标为停用并留理由；之后不会因为战绩复活 |

程序把关：只动候选条目（种子和正式条目只按战绩升降）；合并目标必须有效，顺着同一批合并找最终目标，绕圈或落到被删的条目就改为保留；被验证确认过的候选不能删；没有理由的决定不算。整理之后自动重跑回归集，命中率比整理前低就自动回滚。排查记录里引用的旧条目 id 会顺着合并找到最终条目。

触发：建字典之后马上整理一次；排查学到新候选、服务每 30 分钟巡检时，候选有变化且距上次 ≥ 6 小时才整理；手动 `python3 -m replay dict-curate`。结果在 `knowledge/curate_report.json`，字典页上每条显示整理的理由，改动和回滚都记在 `knowledge/changelog.jsonl`。

### 回归集
被自动验证为一致的案例自动存进 `knowledge/cases/`（原因阶段的完整输入和确认的归类）。字典条目状态变化或新增候选后，自动（最少隔 6 小时）用当前字典重跑最近 20 个案例，算命中率和完整率，记在 `knowledge/regression.json`，字典页上能看到变化。手动重跑：`python3 -m replay diagnose-regress`。

## 配置与成本
- MiniMax：网关地址和密钥用 `REPLAY_SECRETS/ai.env`（`AI_BASE_URL`、`AI_API_KEY`）；模型默认 `minimax-m3.1-flash`（M3 有 5 小时额度，不给排查用），可用 `REPLAY_DIAG_MODEL` 换。
- Femini：只通过白名单里的查询工具（`ReadOnlyFemini`），写入类工具一律拒绝。
- GitHub：`REPLAY_SECRETS/github.env` 的令牌或本机 `gh`，只发 GET。
- 一次排查两次模型调用（原因、验证），实测约 4–5 万 token 输入；每次回访一次模型调用（只验证，不重做原因）；字典页和日期标记不调模型。
- 建字典（2026-10-30 首次）：搜到 671 张 spend 单子、595 簇，读 360 张代表单子，抽出 147 个模式（103 个对上已有条目，新增 32 个候选），约 23 万 token 输入、40 万 token 输出，17 分钟。

## 已知局限
- 合作方原始报告只有 Femini 登记过的 20 个来源（Vizio、Beeswax、Remerge 等），Freewheel 等走仪表盘的合作方无法反查 line item，页面会写明。
- 修复状态里的「数据现状」看的是现在的数据：错录已经被改回的，信号会消失，结论要靠沟通记录和 GitHub。
- Slack 读直连副本（`raw/feed/slack`，每次刷新回放时更新）；最近一次刷新之后的聊天可能还没有。
