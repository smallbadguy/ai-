# 回放服务化计划（待确认后再执行）

状态：已实施并部署到 feedmob1（本地提交，未 push）。服务按 click URL 编号支持多个案子，运行方式见 `README.md`，事件格式见 `docs/事件格式.md`。下文是最初的计划，保留作背景。

## 目标

把现在"AI 查完、手工写进脚本"的做法，变成一条可重复运行的流程：服务器定时或按需，用 MCP 只读拉取 GitHub、HubSpot（Brain 副本）、Slack（Brain 副本）、后台记录的数据，统一格式后生成中英两版页面。

## 四个阶段

### 阶段 1：统一数据格式

- 每个来源的原始记录统一落到 `raw/<来源>/<案例号>/<查询时间>.json`，并记录查询时间和查询参数。
- 定义一份事件 Schema（时间、来源、人员 ID、动作、对象、原文摘录、证据来源）。
- `build_case.py` 只读 `raw/` 生成事件，不再手写任何事实。
- 缺口用配置声明（例如 HubSpot 没有状态变更历史），不靠人填。
- 完成标准：换一个案例号，只改编号就能跑出结构相同的数据。

### 阶段 2：搭建服务

- 一个轻量服务（建议 Python，和现在脚本一致），提供：
  - `POST /build/<案例号>`：触发一次采集与生成；
  - `GET /case/<案例号>/en` 和 `/zh`：返回生成好的页面；
  - 健康检查接口。
- 任务串行执行，同一案例不并发；每次生成保留上一版，失败不覆盖。
- 页面仍是静态单文件，服务只负责生成和分发。

### 阶段 3：接入 MCP 工具

- 采集模块分来源实现，每个只调用只读接口。
- 每个采集器只允许 GET 类操作，代码里做白名单，防止误写。
- 需要的 MCP 服务（本地当前已配置）：
  - `brain`：HubSpot 工单副本、Slack 频道副本；
  - `femini`：后台 23959 利润率变更记录；
  - `mobius`：如需补充任务信息（可选）；
  - GitHub 仍用 `gh` 只读命令。
- 不接入 `beeswax`、`fm-vault-mcp` 等与本案无关的服务，避免扩大权限面。

### 阶段 4：部署到服务器

- 运行在服务器上，由 systemd 或 Docker 常驻（二选一，待你确认）。
- 对外只开放需要的路径，页面访问需要鉴权或仅内网访问（待你确认）。
- 发布前先在服务器上跑一遍完整流程，核对中英两版数据一致后再开放。

## MCP 凭证的搬运方式

- 凭证**不写进代码、不写进仓库、不写进文档**。
- 服务器上放一个只有运行用户可读的环境文件（权限 600），变量名由服务启动时读取。
- 本地的凭证由你在服务器上亲自填写或从本地安全地拷贝，我不在对话里复述任何令牌。
- 搬运完成后，建议轮换一次本地用过的令牌，避免两边同时有效。
- `.gitignore` 已忽略 `raw/`；环境文件放在仓库外。
