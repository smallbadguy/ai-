# Campaign 回放 Dashboard：数据源与实现方案

> 文中有同事真名和业务数字（示例案例用的是真实数据），仅限公司内部使用。

## 1. 这份文档讲什么

用我们已有的 **GitHub、HubSpot、Slack、公司后台** 四类数据，以一个 **campaign 为案号**，还原这条线上"谁、在什么时候、对谁、做了什么、谁接了谁的单子"，做成一个**可以回放的 Dashboard**。

文档回答四件事：

1. 有哪些数据源，每个能拿到什么、拿不到什么；
2. 需要具备哪些工具和接入能力；
3. 数据怎么整理成可以回放的事件；
4. 界面怎么做，做到什么程度，怎么校验。

示例案例：**案号 23959**（Binance 越南 CTV）。完整的参考答案在附录，可以拿来对照自己的结果。

## 2. 目标产出

一个打开就能看的网页，具备：

- 选定一个 campaign，从头到尾**按时间播放**，也能一步步前进后退、点时间轴跳转；
- 每一步显示：**谁**做了什么、**对谁**、在**哪个系统**、**出处**是什么；
- 能看到每个时间点**谁手上有哪张单子**；
- 能看到数据**哪里不准、哪里缺**；
- 只还原真实发生的动作，不加推测。

## 3. 示例案例：campaign 23959

| 项 | 内容 |
|---|---|
| 案号 | **23959**（click URL 编号） |
| 所属活动（后台里的 campaign） | 5165　`Binance_CTV_VN_CPM_OpenMarket_FeedTV` |
| 客户 / 渠道 / 归因 / 系统 | Binance / Freewheel / AppsFlyer / iOS |
| 国家 | 越南 |
| 时间范围 | 2026-08-27 03:35 UTC 至 2026-10-07 08:26 UTC |
| 规模 | 39 个事件、15 个成员（12 位同事 + 3 个机器人） |

> **口径提醒：** 业务上说"campaign"多数指 5 位的 click URL 编号（如 23959）；后台里的 campaign 是它的上一层，5165 下面有多个 click URL。做之前先对一下口径。

**这个案子讲了两件事：**

- **第一幕：上线与追踪花费（8/27–9/25）。** 需求方在 Slack 宣布越南获批开跑 → 生成链接 → 请同事开跑、传素材；随后为追踪花费建 GitHub 单 #14453，经过指派、开发、评审、合并、被打回一次、再验收、关单，共 11 天 18 小时；期间后台调了 7 次利润率（10→20→25→40→20→30→25→20，%）。
- **第二幕：亚太数据中心费并入每日花费（10/6–10/7）。** Slack 提醒 → 需求方回复 → HubSpot 建单、转交负责人 → 建 GitHub 单 #14633 → 指派开发和验收 → 群里确认费用怎么按天摊 → 提交代码、评审、合并，从建 GitHub 单到合并 13 小时 57 分，单子到现在还开着。这一幕横跨 Slack、HubSpot、GitHub，9 位同事加 2 个机器人，最适合演示"谁给谁发的、谁接了活"。

**选案例的四条标准**（换案例时先对照）：

1. 有提单：HubSpot 上有对应单子；
2. 有接单：GitHub 上有对应单子，能看到谁指派、谁接、谁评审、谁合并；
3. Slack 里有讨论：能看到需求怎么在群里提出来；
4. 后台有改动记录：能查到谁在几点改了什么。

**不要按 campaign 编号批量搜。** 抽样发现：主仓库最近的单子里只有约 27% 在标题或正文写了编号，另一个仓库只有约 4%；在大脑里直接搜编号召回也很差。正确做法是**先选定一个案子，从 GitHub 单号出发往外对**。

## 4. 数据源与接入能力

|---|---|---|---|---|
| **Brain MCP**（公司大脑，也叫 gbrain） | 必需 | 读 Slack 副本和 HubSpot 副本 | `sources_list`、`request_tools`、`search`、`query`、`list_pages`、`get_page` | 共 68 个工具，只用以上读取类 6 个；其余用之前先确认会不会写入。需要有 `ken-slack`、`ken-hubspot` 的读权限 |

### 4.2 数据源明细

| 数据源 | 读什么 | 怎么读 | 能拿到 | 局限 |
|---|---|---|---|---|
| **GitHub** | `feed-mob/feedmob`（单子）、`feed-mob/feedmob_worker`（代码合并请求 PR） | `gh api` 现查 | 每张单子每一步：谁指派、谁改标签、谁评论、谁提交、谁评审、谁合并，**精确到秒** | 创建人多是代建的人，真正的提出人要看标题尾巴 `(From 谁 via hs/slack)`；正文里的截图没读 |
| **HubSpot** | 提单内容、负责人、状态、备注 | Brain 的 `ken-hubspot` 副本，页面 `tickets/<短号>` | 建单和最后更新时间**精确到秒**；内容、负责人、优先级、状态、带时间的备注；标题带 `GH#单号` 可对上 GitHub | **仍没有逐项状态变更历史** |
| **Slack** | #binance、#allypod_devs、#mighty-team、#monitor-system | Brain 的 `ken-slack` 副本，页面 `channels/<频道名>-<id>/<日期>` | 需求提出、回复、转交、派单机器人每天的分配摘要、改价播报 | 副本每天凌晨同步一次，示例案例只到 2026-10-07 02:42 UTC |
| **公司后台** | click URL、活动、利润率调整 | Femini `get_click_url`、`get_campaign` | 属于哪个活动、各时段利润率、**谁起草、谁提交、谁批准，精确到秒** | 只用查询类工具 |
| 邮件 | — | Brain 有 `ken-gmail` 副本 | **暂不纳入**（敏感度高） | — |

### 4.3 取数要点（都是实测踩出来的）

- **时间一律是 UTC**，页面里再换算成北京时间。
- **GitHub 的"指派"要看 `assigner`。** issue events 里 `assigned` 事件的 `actor` 反而是被指派的人；timeline 接口里的 actor 才是动手的人。
- GitHub 全量取数加 `--paginate --slurp`（每一页是一个元素，要自己拍平）。
- **GitHub 一律用 `gh` 现查，不用大脑里的 GitHub 副本**：副本缺"谁几点接手、谁评论"。
- **Slack 用 `get_page` 取整天**，比按关键词或编号搜索可靠。
- 大脑里 Slack、HubSpot、邮件是"隔离"数据源：不参与默认检索，**必须显式指定 source**。
- 后台 `get_click_url` 要传 `name="23959"`（编号当名字传）；`list_proposed_changes` 的 `click_url_id` 参数无效，不要用。
- **标题标签：** `[V:验收|D:开发|C:代码评审|P:产品|Q:测试]` 后面跟人名，如 `D:roofeel`，由机器人每天凌晨改标题打上。
- **标签流程（按 #14453 的走法推断，非官方定义）：** in progress → Code Review → PR → Self Check → PA Production Verify → QA（通过）或 enhancement needed（打回）→ 关单。
- **派单机器人：** GitHub 账号 `feedmob-deploy` 每天约 UTC 00:10 给没人接的单子改标题并指派验收人；Slack 里 `FeedmobWorkerNg` 同一时刻发分配摘要。两者是不是同一套程序，是按时间和内容推断的。
- **FeedAI 机器人**（GitHub 账号 `feedmob-qa`）会在单子里贴摘要评论。**摘要里 @ 的 `yi`、`alyssa` 是两个与公司无关的外部账号，机器人认错了人，要忽略。**
- 后台的利润率调整，和 Slack #monitor-system 的播报是**同一秒**，可以互相印证。

### 4.4 环境自检

下面三项都能返回内容，说明这个案例需要的数据都读得到：

1. `gh issue view 14633 -R feed-mob/feedmob`
2. 大脑 `get_page`：`source_id=ken-hubspot`、`slug=tickets/5087`；以及 `source_id=ken-slack`、`slug=channels/binance-c07m207qkef/2026-10-06`
3. 后台 `get_click_url`：`name="23959"`

## 5. 数据方案：把一切变成"事件"

### 5.1 事件模型

不管数据在哪个系统，每个动作都整理成同一种事件：

> **谁**　**在几点**　**做了什么**　**对谁 / 交给谁**　**在哪个系统**　**凭什么这么说（出处）**

有了统一的事件，时间线、对话流、流水账、看板都只是同一份数据的不同排法。

| 字段 | 含义 |
|---|---|
| `ts` | 时间（UTC） |
| `src` / `srcs` | 主来源 / 涉及的来源（github、slack、hubspot、femini） |
| `kind` | 动作：ask 提出、create 新建、assign 指派、chat 对话、notify 播报、comment 评论、label 改标签、pr 提交代码、review 评审、merge 合并、close 关单、change 调价 |
| `actor` / `to` | 谁做的 / 对谁、交给谁 |
| `title` / `text` / `quote` | 一句话标题 / 白话说明 / Slack 短句原话 |
| `ref` / `link` | 出处文字 / 原件链接 |
| `ticket` / `holders` | 属于哪张单子 / 这一步之后谁手上有这张单子、角色是什么 |
| `margin` | 此刻利润率（只有调价事件有） |
| `prec` | 时间精度：`sec`（秒）或 `min`（分钟，页面上显示"约"） |
| `flag` / `flag_text` | "问题 / 注意"标记及说明 |

一条真实的事件：

```json
{
  "ts": "2026-09-25T03:06:22Z",
  "src": "femini", "srcs": ["femini", "slack"],
  "kind": "change", "actor": "liwei", "to": ["delivery"],
  "title": "Liwei 把利润率从 25% 调到 20%",
  "ref": "后台 get_click_url(23959) 调整 #265492；Slack #monitor-system 2026-09-25 03:06:22 UTC",
  "prec": "sec"
}
```

**最低要求：** 不管界面做成什么样，每条事件至少有时间、谁、做了什么、对谁、来源、出处这六项。

### 5.2 整体流程

```
 GitHub（gh 现查）────┐
 HubSpot（大脑副本）──┤
 Slack  （大脑副本）──┼─▶ 对人、对时间、核对 ─▶ 整理成事件（JSON）─▶ 回放页面
 后台   （Femini）────┘
```

### 5.3 做事步骤

1. **定案例。** 按第 3 节四条标准选。
2. **取 GitHub。** 对选定的单子取三样：`/events`、`/timeline`、`/comments`。再从 timeline 里的 `cross-referenced` 事件找到关联的代码合并请求，取它的 `/reviews`、`/commits`、`/files`（文件只留文件名和增删行数，不存代码内容）。
3. **取 HubSpot。** 用标题里的 `GH#单号` 找到对应单子，读内容、负责人、备注。
4. **取 Slack。** 找到相关频道在相关日期的**整天页面**，摘出与案子直接相关的几句，只摘短句。
5. **取后台。** 用案号查它属于哪个活动、利润率调整记录（谁起草、谁提交、谁批准）。
6. **对人。** 把"GitHub 账号 ↔ Slack 名字 ↔ 真名"对上，记依据和把握（高 / 中）。依据不足的标"中"，交业务同事确认。
7. **整理事件。** 每条带出处。GitHub 的时间和人从原始记录里取，不手抄；脚本里加断言，对不上就报错。
8. **做页面、核对。** 见第 6、7 节。

### 5.4 串联规则

- **GitHub 为主轴**，HubSpot 用 `GH#单号` 挂上，Slack 用日期和频道挂上，后台用案号挂上。
- 能精确到秒的用原始时间（GitHub、后台、HubSpot 的 `hubspot_created_at` / `hubspot_updated_at`）；只有分钟精度的才标 `prec=min`，页面上写"约"。示例 HubSpot 单 5087 的建单时间可直接从大脑读到 **2026-10-06 15:19:43 UTC**，不再依赖机器人的分钟级摘要。
- 事件文字里**不要写死钟点**（页面默认北京时间，会和 UTC 钟点矛盾），用"7 秒后""5 小时后"这类相对时间。
- 机器人**单独作为成员**，因为它们在流程里确实动手了（派单、贴摘要、播报）。

### 5.5 可选的数据方案

| 方案 | 做法 | 能做到 | 局限 |
|---|---|---|---|
| **A（当前示例）** | HubSpot、Slack 读大脑副本；GitHub 用 `gh` 现查；后台用 Femini | 无需额外权限，HubSpot 建单和最后更新可精确到秒 | HubSpot 没有逐项状态变更历史；Slack 副本有同步延迟 |
| **B（可选）** | 如果将来要回放 HubSpot 的每次状态变化，先确认能否从源系统或同步服务拿到完整历史 | 有历史记录且获得相应只读权限后，才可增加"谁何时把状态改成什么" | 目前没验证这些历史能否读取，不承诺精度 |
| **C** | 在 B 的基础上加邮件 | 能还原邮件往来 | 敏感度高，要先确定可以放进回放的范围 |

## 6. 界面方案

### 6.1 页面布局

- **顶部：** 案号和名称、各数据源状态（正常 / 受限 / 未纳入）、幕切换、时区切换。
- **播放条：** 播放 / 暂停、1x/2x/3x、时间轴（点击或拖动跳转）、跳到最新；空格播放，← → 一步一步走。
- **核对清单：** 几条"是否已核对"的勾选项（如 GitHub 已读、Slack 已读、后台已读、人物对应已核对、没有写入任何系统）。
- **左侧成员栏：** 同事、机器人分组，显示每人此刻状态（持有单子 / 已交棒 / 出场 / 未登场）。
- **中间：** 多个视图和页签（见 6.2）。
- **右侧：** 证据（如利润率走势、各来源说了什么、一段总结）和选中成员的详情。
- **底部：** "现在谁手上还有单子"。

### 6.2 视图和页签

| 视图 | 内容 | 数据 |
|---|---|---|
| **Ladder（梯形图）** | 每个成员一列，时间向下，每一步一张卡片，写明谁做了什么、对谁、读自哪个系统；手上有单子的成员列亮条 | `events` |
| **Thread（对话流）** | 像群聊一样按时间排的事件，按天分隔 | `events` |
| **Log（流水账）** | 按时间排的流水，带来源和动作 | `events` |
| **3D（空间）** | 离线内嵌的空间场景：每条事件一步；人员、机器人、数据源按活动数据生成；事件光包连接人物与来源，交接光包连接发起人与接收人；可切换视角和 2D 平面图 | `events`、`people`、`sources` |
| **Tasks（任务）** | 每个人手上有什么单子、已经交出什么 | `holders` |
| **Connections（数据来源）** | 每个数据源能读到什么、哪里不准 | 来源说明 |
| **Accounts（人物对照）** | 账号对应哪位同事、依据和把握 | 人物表 |

### 6.3 分层目标（不求一步到位）

| 层级 | 做到什么 |
|---|---|
| **最小版** | 一条时间线 + 播放 + 点击看详情；每条事件有六项必填字段 |
| **标准版** | 加成员栏、Ladder / Thread / Log 三个视图、3D 空间视图、时区切换、核对清单 |
| **加分项** | Tasks、Connections、Accounts 页签，右侧证据和成员详情，底部"谁手上有单子" |

### 6.4 3D 场景实现与校验

- 3D 场景、时间线引擎和控制器均作为本地资源内嵌到中英文单文件页面，不依赖外网字体、脚本或数据接口。
- 保留空间场景的星空、镜面地面、人物工作位、机器人机柜、数据源设备、事件塔、光包动画、镜头预设和轨道交互。
- 每条活动事件转换成一个有日期的步骤；人物与来源由活动数据生成。手机分配给事件接收人中的一位同事，屏幕显示当前回放事件；其他同事显示笔记本，机器人显示机柜。
- 播放位置和时区与主回放页同步；事件读取光包、人员交接光包均由实际事件字段驱动，不使用演示账号或固定人员名单。
- 中文界面翻译场景内的控件、图例和设备状态；英文场景不得有汉字。页面切换语言不改变事件内容和时间顺序。
- 生成后运行自动测试，并用真实活动检查 1280 和 1920 宽度、3D 是否启动、场景人数与事件数、英文汉字和浏览器报错。

## 7. 约束与校验

**约束**

1. **全程只读。** GitHub 只发 GET；Slack、HubSpot 只读大脑副本；后台只用查询类工具。不往任何系统写内容。
2. **不需要也不要操作 Slack 本体。** Slack 内容只读大脑副本，原话只摘短句，不放整段聊天。
3. 事件描述里直接写名字，不用性别代词。
4. 页面是内部版，含真名和业务数字，不外发；给客户看的匿名版需要另做。
5. 原始取数文件含评论原文，不要提交进代码库。

**校验清单**

- 每条事件都有出处，查不到就写"没查到"，不要编；
- GitHub 的时间和人从原始记录取，脚本里断言；
- 对不上的人名和账号标"把握：中"，交同事确认；
- 把每条事件文字通读一遍，查错字和张冠李戴；
- 页面里写明数据哪里不全（比如 HubSpot 没有逐项状态变更历史），不要藏；
- 和附录的参考答案对照，看有没有漏人、漏步骤。

## 8. 已知局限

1. HubSpot 副本现在有建单时间和最后更新时间（秒级），但没有逐项状态变更历史；回放里仍没有"谁几点改了状态"。
2. Slack 副本有同步延迟：示例案例只到 10/7 02:42 UTC，看不到 Summer 问"1500 ÷ 26 天是不是多算了一天"之后有没有回复。
3. 标签流程是按 #14453 的走法推断的。
4. 人物对应有 5 项把握只有"中"：Holly、Circle、Mandy、Lunar、派单机器人，需要同事确认真名。
5. 示例案例的核对清单 5/6 通过，尚待确认的是"人物对应已核对"。

## 9. 建议的实施路线

| 阶段 | 做什么 | 做到什么算过 |
|---|---|---|
| 1 能读到 | 跑第 4.4 节环境自检 | 三项都有内容返回 |
| 2 整理事件 | 选一张单子（如 #14633），整理成事件，哪怕只有 10 条 | 每条有六项必填字段 |
| 3 最小回放 | 一条时间线 + 播放 + 点击看详情 | 能从头播到尾，能点任一步看详情 |
| 4 多视图 | 加成员栏、Ladder / Thread / Log、3D 空间 | 各视图能互相切换，时间一致 |
| 5 核对 | 找出哪里不准、哪里缺，写成一段话 | 讲得清"这份回放哪里可信、哪里不确定" |

各阶段都可以独立完成；界面的做法允许有自己的想法，只要事件字段和出处这两条守住，成果就可以互相对照。
