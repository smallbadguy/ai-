# AI 任务外包队列

生成回放时，「进行中事项」「业务版」要调很多次大模型。每一次调用就是一道「题」：一段工作说明（system）加一段材料（user），要求交回一个 JSON 对象。
外包队列把这些题放出去：处理方每分钟来领一道、做完交回。所有 AI 处理都走队列（2026-10-31 用户要求），
我们自己的处理方（公司网关的 MiniMax Flash）也只是一个普通处理方：各自一把钥匙，走同一套接口领题、交答案，没有捷径。

代码：`replay/jobqueue.py`（队列和全部规则）、`service/agent_api.py`（给 agent 的接口）、`service/ai_worker.py`（自家处理方）、
`service/queue_page.py`（状态页）、`service/agents.py`（登记命令）、`service/queue_batch.py`（用队列批量补完活动）。
给外部 agent 的接入注册说明：`docs/agent接入注册.md`（`GET /agent-api/v1/protocol` 返回的就是它，改文档不用重启）。

## 为什么按「一次 AI 调用」外包
- 题目自带全部材料，agent 不需要我们的代码、数据或任何系统权限，读完交一个 JSON 就行。
- 交回来的答案照旧经过流水线的程序核对：原话要在原始记录里逐字找到，说话人和时间取原始记录。不管哪个 agent、什么模型，编造的话都上不了页面。

## 状态
| 状态 | 意思 |
|---|---|
| 排队中 queued | 等处理方来领 |
| 处理中 leased | 某个处理方领走了，截止时间之前要交回（可续期） |
| 已完成 done | 收到了第一个合格的答案 |
| 失败 failed | 反复超时或不合格（满 6 次），或者所有处理方都读不下 |
| 已作废 cancelled | 没有流水线在等这道题了 |

## 规则
1. 一个处理方同时只拿一道题；没交之前再来领，拿到的还是同一道。
2. 领题时给截止时间（40 分钟，2026-10-31 用户定），可续期，一次领取最长 60 分钟。过了截止时间没交 = 失联：题目重新排队，换人做。
3. 一道题只认第一个合格的答案（先到先得）：
   - 失联后才交回的旧答案，只要题目还没完成（包括已判失败的）照样收下；正在做同一道题的处理方，下次续期或交答案时被告知停止。
   - 题目已经有人完成了，迟到的答案回 409，只记一笔，不用。
   - 失联后又回来续期，题目还没人领：接着做（「超时后续上」）。
   - 过了截止时间才交的，不管中间有没有别人来过，都记成迟到、算这个处理方一次超时（答案合格照样收）。
4. 答案不合格当场退回原因，题目没完成之前可以改了再交；一次领取最多交 7 次，交满还不合格算这次失败。不合格指：不是标准 JSON 对象（含 NaN、Infinity 也不行）、缺少题目要求的顶层字段、或者这个字段的样子不对（照题目说明里的输出模板查，比如该是对象列表却给了一段文字）。答案外面包着思考过程、代码块标记或一两句话可以，收下时只存读出来的 JSON。
5. 同一道题失败（超时 / 交满 7 次仍不合格 / 放弃）满 3 次，只交给自家处理方；满 6 次算失败，流水线这一步报错，页面保留上次成功的版本。
   放弃时注明 `retryable: true`（网关限流、处理方重启这类不是题目本身的问题）不算失败。
6. 连续超时 3 次的处理方暂停领题 30 分钟；交上一个合格答案就清零。
7. 一模一样的题（内容逐字相同）只做一次：做过的直接复用答案，排着或做着的就等它。流水线中途重启再跑，做过的题不会重新外包。
8. 排队的题超过 15 分钟没有流水线来取结果（流水线进程已经不在了），作废；作废之后交回的答案不收。
9. 时间一律 UTC 记下：出题、原料取数（这份材料是我们什么时候取的）、原料截至（材料里最新一条记录）、领题、取题、续期、交回。状态页按北京时间显示。
10. 优先级：首页手动刷新、每天的定时刷新出的题是 0，最先派；批量出的题是 1、2、3…（`AI_QUEUE_PRIORITY=<活动的先后>`），
    数字越小越先派——先开始的活动先做完，页面一个个出来。一模一样的题重复出时按更靠前的算。
11. 不调 AI 的活儿（取数据、整理原料、生成页面）整台服务器排队，一次只做一个活动（`pipeline._server_turn`，2026-10-31 用户定）；
    批量、每天的刷新、首页刷新都排这一个队。AI 那几步在队列里等答案，不占这个位置。

## 按大小派题（不切题）
- 处理方登记时写明一次能读多少 token（模型上下文，例如 200000、1000000）。
- 每道题估算 token：中日韩文字一个字算一个，其余每 3 个字符算一个（宁可估多）。题目 + 4 万（留给思考和答案）不超过登记值的 85%，才派给它。
- 派题顺序：先按优先级（数字小的先），同一优先级里最小的处理方读不下的大题先派给读得下的大处理方，再按出题先后。
- 自家处理方（1M）和外部处理方一视同仁，谁先来谁领；唯一的区别是失败满 3 次的题只交给它。
- 排队超过 10 分钟、所有启用的处理方都读不下的题判失败（不让流水线干等 6 小时）；一个处理方都没登记时不判，等有人登记。

## 开关
- `AI_EXECUTOR=queue`（进程环境变量，或写进 stage 的 `secrets/ai.env`）：流水线的 AI 调用改走队列。不设就照旧直接调网关，和以前一样。
- 自家处理方：stage 上的 systemd 服务 `ai-2734-replay-stage-worker`（`deploy/ai-2734-replay-stage-worker.service`），
  `AI_WORKER_SLOTS` 个（internal-1 … internal-N，2026-10-31 下午用户定 8 个，凌晨是 2 个），模型 `minimax-m3.1-flash`，一次能读 1M。
  启动时自己登记、拿钥匙（存 `secrets/internal-agents.json`），之后只通过 `http://127.0.0.1:8792/agent-api/v1` 和外部一样领题、交答案。
  网关限流时把题退回（`retryable`，不算失败），歇 10 分钟再领；接口连不上（网页服务重启）就等一会儿，做好的答案多试几次再交；重启时把手上的题退回。

## 登记处理方（在 stage 服务器 app 目录下）
```
python3 service/agents.py add hermes --context 200000 --model claude-sonnet --note "Hermes 定时任务"   # 打印钥匙，只显示一次
python3 service/agents.py list
python3 service/agents.py set hermes --context 1000000      # 换了模型、上下文变了
python3 service/agents.py disable hermes / enable hermes
python3 service/agents.py token hermes                       # 换钥匙，旧的立即失效
python3 service/agents.py unpause hermes                     # 解除连续超时暂停
```
钥匙只存摘要；丢了就换一把。

## 给 agent 的接口
前缀 `https://replay-stage.feedmob.it.com/agent-api/v1`，请求头 `Authorization: Bearer <钥匙>`。完整接入说明：`GET /agent-api/v1/protocol`（不需要钥匙）。

| 接口 | 作用 |
|---|---|
| `POST /claim` | 领题。没题返回 `{"job": null}`；领到返回题号、领取号、截止时间、大小、原料时间 |
| `GET /jobs/<题号>/input?lease=<领取号>` | 取题：messages（system + user）、原料取数/截至时间、答案要求的顶层字段 |
| `POST /jobs/<题号>/heartbeat` `{"lease_id"}` | 续期；`continue: false` 表示题目已完成或作废，停下；`reassigned: true` 表示超时后题目已给别人，合格答案仍可交 |
| `POST /jobs/<题号>/result` `{"lease_id", "output", "model"}` | 交答案：200 收下；422 不合格（附原因，可改了再交）；409 题目已完成或作废 |
| `POST /jobs/<题号>/release` `{"lease_id", "reason", "retryable"}` | 放弃，题目马上重新排队；`retryable: true` 不算这道题失败 |
| `GET /me` | 自己的登记信息和统计 |

## 状态页
`https://replay-stage.feedmob.it.com/queue`（公司 Google 账号登录）：
- 处理方：模型、一次能读多少、此刻在做哪道题、完成 / 超时 / 被退回 / 迟到 / 放弃次数、平均用时、最近来过。
- 各活动最近两天的任务数（按状态）。
- 任务列表：可按状态、活动筛选；点题号看这道题的完整经过（每次领取、取题、续期、交回、收没收、为什么）。
首页正在处理的活动，状态下面会显示「AI 任务 a/b 已完成」。

## 用队列补完活动（批量）
`service/queue_batch.py`：全部没做完的活动都排上，活动编号从大到小；第 k 个活动出的题优先级是 k（先开始的先做完）。
同时开着的活动最多 8 个（`QUEUE_BATCH_LANES`）：服务器只有 2 核、8G，还跑着公司的网关，每个开着的活动占 60MB 上下，
187 个一起开会把机器撑爆；一个做完自动接下一个。批量的题每道最多等 48 小时（`QUEUE_BATCH_WAIT_HOURS`，平时是 6 小时）。
- 只缺业务版的（有原料、有详细版）：只补 AI 两步和页面，不重新取数（`refresh.py --fill-ai <编号>`，`pipeline.fill_ai`）。
  详细版「数据来源」沿用上次真正取数时记下的 GitHub、后台与大脑状态。
- 从没生成过的：跑完整流程（`refresh.py <编号>`）。
- 正在处理的活动跳过；只跑一遍，最后列出没做成的。日志 `../logs/queue_batch.log`，结束标志 `QUEUE-BATCH-DONE`。
